# OPT Home Inventory

OPT Home Inventory tracks the items in a home: what you have, where it is, and when it
expires. You talk to it in natural language — "add two cartons of milk to the fridge,
they expire next Friday", "I used the last of the rice", "what expires this week?" — and
it updates the inventory or answers the question. Everything runs on the device: speech
recognition, language understanding, date resolution and storage all work offline.

> **Status: manual inventory.** The Android app lists the inventory with search, adds
> items through a form, and opens an item when it is tapped to edit or delete it; items
> are stored in SQLite by the Rust core. The chat box at the bottom accepts text but does
> not act on it yet: natural-language requests (Llama) and speech input are still to come.

Built with Llama.

## Architecture

```
┌──────────────────────────────────────────────────────────────┐
│ React Native UI (TypeScript)                  app/           │
└───────────────────────────────┬──────────────────────────────┘
                                │ JSI Turbo Module (generated)
┌───────────────────────────────┴──────────────────────────────┐
│ core-bridge                                  packages/       │
│ TypeScript + C++ bindings from uniffi-bindgen-react-native   │
└───────────────────────────────┬──────────────────────────────┘
                                │ uniffi C ABI
┌───────────────────────────────┴──────────────────────────────┐
│ Rust core (inventory-core)                   core/           │
│  ├─ SQLite (rusqlite, bundled)       storage                 │
│  ├─ Duckling (Rust port)             date resolution         │
│  └─ inference-sys                                            │
│      ├─ llama.cpp + Llama 3.2 1B     language understanding  │
│      ├─ whisper.cpp + Whisper small  speech-to-text fallback │
│      └─ ggml (one copy, shared by both engines)              │
└──────────────────────────────────────────────────────────────┘
```

| Concern | Technology | Notes |
|---|---|---|
| UI | React Native 0.83.10, New Architecture, TypeScript | 0.83 is the newest version supported by both `react-native-macos` and `react-native-windows`, so one RN version can serve every planned platform. |
| Backend | Rust library linked into the app (`core/crates/inventory-core`) | In-process, not a server. Its API is defined once with [uniffi](https://mozilla.github.io/uniffi-rs/). |
| Rust ↔ JS | [uniffi-bindgen-react-native](https://github.com/jhugman/uniffi-bindgen-react-native) (ubrn) | Generates the TypeScript API, a JSI C++ Turbo Module and the Android library module in `packages/core-bridge`. |
| Storage | SQLite via `rusqlite` (`bundled`) | The same SQLite version is compiled in on every platform. |
| Language model | [llama.cpp](https://github.com/ggml-org/llama.cpp) v0.9.0 + Llama 3.2 1B Instruct (Q4_K_M, 808 MB) | Turns requests into structured actions (later). |
| Speech-to-text | [whisper.cpp](https://github.com/ggml-org/whisper.cpp) v1.9.5 + Whisper small (q5_1, 190 MB) | Fallback when the OS has no native speech recognition. |
| Dates | [`duckling`](https://crates.io/crates/duckling) 0.4.0, a Rust port of Facebook's Duckling | Resolves phrases like "next Friday" or "in 3 weeks" to dates. |

### How a request will flow (future)

1. Speech is transcribed by the platform recognizer (Android `SpeechRecognizer`, iOS
   `SFSpeechRecognizer`) or, where none is available, by whisper.cpp.
2. Llama 3.2 1B extracts the intent (add / remove / query), the item, quantity, location
   and any date phrase.
3. Duckling resolves the date phrase against the current date.
4. The Rust core applies the change to SQLite or answers the query, and the UI updates.

### Native build design

whisper.cpp and llama.cpp each vendor their own copy of **ggml**, and linking two copies
into one library gives duplicate (or silently mismatched) symbols. `inference-sys` avoids
this with a CMake superbuild (`core/crates/inference-sys/native/CMakeLists.txt`): it adds
llama.cpp first, so its ggml becomes the only `ggml` target, and whisper.cpp then skips
its own copy. The Rust FFI is generated by bindgen and committed
(`core/crates/inference-sys/src/bindings.rs`), so normal builds do not need libclang.

On Android the Rust core is built as a static library per ABI with `cargo-ndk`; ubrn's
CMake file links it into `libcore-bridge.so` together with React Native's libraries. All
native code uses the shared `c++_shared` runtime, the same one React Native uses.

## Inventory data

Items live in one SQLite table, `items`, created by the migrations in
`core/crates/inventory-core/src/db/migrations.rs` (`PRAGMA user_version` tracks the
schema version):

| Column | Type | Notes |
|---|---|---|
| `id` | integer, `AUTOINCREMENT` | Never reused, so a stale id (e.g. from a pending Llama action) fails with `NotFound` instead of changing another item. |
| `name` | text, required | The item, e.g. "Milk 1 gallon". Search matches any part of it, case-insensitively. |
| `location` | text, required | Free text; a location matching an existing one case-insensitively reuses its spelling. |
| `quantity` | integer ≥ 1, default 1 | An item whose quantity reaches 0 is deleted (`set_item_quantity(id, 0)`), never stored as 0. |
| `expiration_date` | `YYYY-MM-DD` or NULL | NULL means the item does not expire. |
| `created_date` | UTC timestamp | Set by SQLite on insert; shown as "Added …" in the list. |

The Rust core validates every write and SQLite `CHECK` constraints back it up. If storage
is unavailable or any read or write fails, the app shows an error screen and closes.

## Building for Android

Build host: Linux x86_64 (tested). The scripts also handle macOS, but that path is
untested. Building needs about 15 GB of disk for the toolchains, models and build
outputs.

### Prerequisites

Install these yourself: `git`, Node.js 20 or newer (`.nvmrc` pins 24), Yarn (any version;
the repo runs its pinned Yarn 3.6.4 from `.yarn/releases`), CMake 3.22+, `make`, a C/C++
compiler for the host, `curl` and `unzip`.

Everything else — JDK 17, the Android SDK, NDK 27.1.12297006, Rust 1.99.1 and
`cargo-ndk` — is installed by the bootstrap script into your home directory, with no
`sudo`.

### Steps

```sh
git clone --recurse-submodules --shallow-submodules https://github.com/KristopherTadlock/home_inventory_app.git
cd home_inventory_app

./scripts/bootstrap-android.sh        # add --e2e for the emulator image and Maestro
source scripts/lib/env.sh             # JAVA_HOME, ANDROID_HOME, PATH for this shell
./scripts/build-android.sh            # add --no-models for a small APK without models
```

The build downloads and verifies the models, builds the Rust core for `arm64-v8a` and
`x86_64`, regenerates the bridge, and produces:

| APK | Path | Size |
|---|---|---|
| Debug | `app/android/app/build/outputs/apk/debug/app-debug.apk` | ~1.1 GB |
| Release (signed with the debug keystore) | `app/android/app/build/outputs/apk/release/app-release.apk` | ~1.0 GB |

With `--no-models` the release APK is about 64 MB. Install with
`adb install -r <apk>`. The debug APK loads JavaScript from Metro, so start it first with
`yarn workspace home-inventory-app start`; the release APK is self-contained.

`scripts/lib/env.sh` assumes the SDK in `~/Android/Sdk` and JDK 17 in `~/.local/jdk-17`;
set `ANDROID_HOME` or `JAVA_HOME` beforehand to use existing installations.

### Behind a proxy

The scripts honour `https_proxy`. Two tools need extra settings in your own environment
(not the repo): Gradle reads proxies only from `~/.gradle/gradle.properties`
(`systemProp.https.proxyHost`, `systemProp.https.proxyPort`, and the `http` equivalents),
and Node's `fetch` (used by the React Native CLI) needs `NODE_USE_ENV_PROXY=1`.

## Testing

Run these after `source scripts/lib/env.sh`:

| Command | What it runs |
|---|---|
| `yarn test` | Jest + React Native Testing Library: screens, form, storage failure handling (in-memory repository; native modules mocked) |
| `yarn typecheck` | TypeScript over the app and the generated bindings |
| `yarn test:rust` | Rust unit tests on the host: schema, migrations, inventory queries and storage failures, Duckling date phrases, both engines |
| `cargo test --manifest-path core/Cargo.toml -- --ignored` | Loads the real models (needs `scripts/fetch-models.sh`) |
| `yarn test:e2e` | Boots a headless emulator, installs the release APK, runs the Maestro flows in `app/e2e/` and checks the on-device self-check log (needs `bootstrap-android.sh --e2e`, KVM on Linux) |

## Working on the code

- **Changing the Rust API** (`core/crates/inventory-core`): run
  `yarn workspace core-bridge ubrn:android` (or `scripts/build-android.sh`) to rebuild and
  regenerate the bindings, and commit the regenerated files in `packages/core-bridge`.
- **Upgrading llama.cpp or whisper.cpp**: check out the new tag in `third_party/`, run
  `scripts/generate-inference-bindings.sh` (needs `cargo install bindgen-cli --version 0.73.2`
  and libclang), then `yarn test:rust` and
  `cargo test --manifest-path core/Cargo.toml -- --ignored`. Both engines must build
  against llama.cpp's ggml.
- **Changing models**: edit `models/models.lock.json` (URL pinned to a revision, size,
  sha256); the Gradle build packages whatever the lock file lists.

## Known limitations

- **Non-English dates.** The Duckling port matches upstream Duckling on 99% of the English
  time corpus but only 39–85% in other languages, sometimes swapping day and month
  (Portuguese "4/7" → April 7). Duckling has no time rules at all for Hindi or Thai. Date
  resolution should be treated as English-only until the port's rules are improved.
- **Duckling memory.** The port caches each language's rules for the life of the process
  (about 25–35 MB per language), so load only the languages a user needs.
- **Model loading.** llama.cpp and whisper.cpp load models from a file path, so the app
  will need to copy them from APK assets to app storage on first run.
- **Store distribution.** A ~1 GB APK exceeds Google Play limits; release builds should
  move the models to a Play Asset Delivery install-time pack.
- **CPU tuning.** ggml is built for each ABI's baseline (`GGML_NATIVE=OFF`): the x86_64
  emulator build reports SSE3/SSSE3 only, and arm64 uses ARMv8-A without dotprod or i8mm.
  Per-CPU variants are future work.
